# Reference (Oracle) Solution Walkthrough

Source: `fromdevcloud/signedgate-object-access/solution/`. This is the
golden implementation the verifier's own test comparisons are benchmarked
against (100/100, 11/11 passed on a clean run).

## Submission layout

```text
submission/
├── deploy.sh
├── destroy.sh
├── manifest.json        # generated by deploy.sh, not checked in
└── infra/
    ├── network.tf
    ├── identity.tf
    ├── storage.tf
    ├── compute.tf
    ├── outputs.tf
    ├── variables.tf
    └── versions.tf
```

## `deploy.sh` mechanics

1. Verifies `terraform`, `jq`, `curl` are on `PATH` and `/workspace/config/config.json`
   is readable. Fails fast (`exit 2`) rather than deep into Terraform if not.
2. Validates the config's shape with a single `jq -e` boolean expression
   (`resource_prefix` ≥3 chars, `region` non-empty, `aws_endpoint_url` matches
   `^https?://[^/]+$`, image fields present, `presign_ttl_seconds` in `(0, 300]`).
3. Writes the dynamic values to **`infra/config.auto.tfvars.json`**. This is
   the detail most graded model runs got wrong (see `model-run-comparison.md`).
   Because Terraform auto-loads `*.auto.tfvars.json`, this makes every
   variable available to a bare `terraform plan`/`apply` run from that
   directory, with no `-var` flags required from any wrapper script.
4. `terraform init` / `apply -auto-approve`.
5. Reads the `manifest` output directly from Terraform state
   (`terraform output -json manifest`) rather than hand-assembling JSON.
   This guarantees the manifest and the live infrastructure can't drift
   apart within one run.
6. Polls `$url/health/ready` (from the manifest's `alb.connect_url`) until
   **6 consecutive** successful checks (not just one), with a 180s deadline.
   Guards against a target group reporting healthy prematurely.

All config reads use the fixed absolute path
`/workspace/config/config.json`, resolved once at the top of the script,
never a path relative to `$script_dir`.

## `destroy.sh` mechanics

Short-circuits cleanly if no state exists (`exit 0`, not an error; repeated
destroy calls are safe). Otherwise re-inits if needed, `terraform destroy
-auto-approve`, then explicitly asserts `terraform state list` is empty
afterward. Destruction isn't trusted just because the command returned 0.

## Terraform structure, file by file

**`network.tf`**: one VPC (`10.42.0.0/16`), 2 public + 2 private subnets
(via `cidrsubnet` offsets, spread across `local.azs`), one IGW, one shared
public route table (to the IGW) versus **one private route table per
private subnet** (no default route at all; this is what makes them
private). ALB security group named with an explicit `signedgate-` prefix
(a comment notes AWS reserves the bare `sg-` prefix for generated IDs, a
subtle naming trap worth remembering for any SG-naming task). API SG
allows 8080 only from the ALB SG's ID, not a CIDR. The S3 gateway
endpoint's `route_table_ids` is set to *all* private route tables' IDs,
and its policy is a single explicit allow-list
(`GetObject`/`PutObject`/`DeleteObject`/`ListBucket`) scoped to exactly
the one managed bucket ARN and its `/*`, not `Resource: "*"`.

**`identity.tf`**: one user pool, one resource server (`signedgate`) with
three scopes, then a `for_each` over a `client_scopes` map to create all
four clients in one block (`viewer` to `viewer`, `contributor_a` to
`contributor`, `contributor_b` to `contributor`, `admin` to `admin`).
This is why the two contributor clients share a scope but have distinct
client IDs/secrets. Separate `execution` and `api` IAM roles: the
execution role's policy is scoped to only
`logs:CreateLogStream`/`PutLogEvents` on the one log group ARN; the API
role is scoped to `s3:ListBucket` on the bucket itself plus
`Get/Put/DeleteObject` **only under `tenants/*`**, DynamoDB CRUD on exactly
one table ARN, and KMS `Decrypt`/`Encrypt`/`GenerateDataKey` on exactly the
two managed keys. No wildcard actions or resources anywhere in this file.

**`storage.tf`**: two KMS keys (object, metadata), each with rotation
enabled, a 7-day deletion window, and one alias. S3 bucket with
`force_destroy = true` (this is *why* destroy can succeed with versioned
objects present: Terraform empties the bucket for you rather than the
script doing it manually), separate versioning/SSE/public-access-block/policy
resources. Bucket policy is a single `DenyInsecureTransport` statement keyed
on `aws:SecureTransport == false`. DynamoDB table: `PAY_PER_REQUEST`,
string PK `file_id`, SSE with the metadata KMS key.

**`compute.tf`**: CloudWatch log group at `/ecs/<task-family>`, 7-day
retention. One internet-facing ALB in the public subnets, one target group
(`target_type = "ip"`, health check path `/health/ready`), one HTTP:80
listener forwarding to it. One ECS cluster, one Fargate task definition
(`awsvpc`, single container, port 8080, all required env vars; see
`environment/workspace/contracts/runtime.md`), one service with
`desired_count = 2`, private subnets, `assign_public_ip = false`, and an
explicit `depends_on = [aws_lb_listener.http, aws_vpc_endpoint.s3]`. The
service won't even attempt to start until both the listener and the S3
path exist, avoiding a race where tasks come up unable to reach S3.

Note the Cognito issuer trick in the container environment:
`COGNITO_ISSUER = "http://localhost:4566/${user_pool_id}"`, a
Floci-specific quirk where the issuer claim needs a fixed local hostname
regardless of the externally-reachable endpoint used for the JWKS URL.

**`outputs.tf`**: a single `manifest` output object, `sensitive = true`,
whose shape exactly matches `contracts/schemas/manifest.schema.json`. Worth
noting: `alb.url` and `alb.connect_url` are **both** set to
`http://${local.endpoint_host}:80` here (the emulator-reachable endpoint),
deliberately *not* the real ALB DNS name. See
`../../platform/scoring-and-gotchas.md` for why conflating this with the
"real" DNS name is the single most common way graded submissions lost
points.

## Manifest contract highlights

Required top-level keys: `deployment`, `network`, `alb`, `compute`,
`storage`, `auth`, `kms`, `logs`, `image`. The `auth` block must carry all
four clients' IDs *and secrets* in the exact field names the schema
specifies (`viewer_client_id`, `viewer_client_secret`, ... ). The verifier
uses these directly to request client-credentials tokens per role, so any
naming deviation breaks every behavioral test at the token-acquisition step
rather than at an assertion.
